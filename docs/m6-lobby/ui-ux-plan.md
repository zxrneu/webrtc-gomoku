# 初版服务大厅：UI 与交互规划

日期：2026-10-19。状态：Node / Rust 服务端 MVP 已实现。

**用户最终调整：大厅独立为 `/lobby` 页面，不展示棋盘。** 桌面端左右布局，手机端纵向布局；入座后切换到棋盘页。实现范围和验证记录见 [实施记录](implementation.md)。下面涉及旧侧栏方案的尺寸和线框仅保留为设计过程参考，以本段与 PRD §3.1 为准。

基于现有 [M6 PRD](prd.md)、React + CSS Modules 界面及 Rust / Node 信令实现。本文件补充可执行的页面和交互设计；用户后续要求的「查看在线用户、邀请组建房间」已同步至 PRD §11，其余设计调整在末尾单独列出。

## 1. 产品定位与首期范围

**让没有约好对手的人，打开页面就能找到一桌棋。**

核心路径是「进入大厅 → 快速匹配 / 加入房间 / 邀请在线棋友 → 建立连接 → 开始对局」。首访自动生成昵称，首次匹配无需填写表单。已有可匹配玩家且连接成功时，从大厅点击一次即可进入对局；定向邀请需对方明确接受，等待时长受在线人数与网络影响，不承诺固定几秒开局。

| 优先级 | 内容 | 初版体验 |
|---|---|---|
| P0 | 大厅入口、临时昵称、真实在线统计 | 不登录；默认昵称可直接使用 |
| P0 | 房间列表、加入、公开建房 | 看清谁在等；点击加入后自动连接 |
| P0 | 在线用户列表、定向邀请组房 | 看见空闲棋友；对方接受后自动建房并为双方入座 |
| P0 | 快速匹配、取消、超时与失败恢复 | 等待有反馈；可退出；不会重复入队 |
| P0 | 断线恢复、旧服务端降级、输入校验与限流 | 错误有出路；大厅故障不影响现有对局 |
| P0 | PRD 的多标签页、隐私与兼容要求 | 纳入开发与验收，不因界面简洁而省略 |
| P1 | 只看等待中、随机换昵称、执色偏好、隐身 | 沿用 PRD 优先级；不阻塞首期主链路 |
| 后续 | 观战、段位、好友、排行榜、规则配置 | 各自立项评估 |

快速匹配首期建议仅撮合匹配队列中的两人；公开房间通过列表主动加入；指定对手则从在线棋友发起邀请。三条入口最终复用同一套双人房间与对局流程。

## 2. 设计依据与视觉方向

按用户指定的 [UI UX Pro Max 官方技能](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/blob/main/.claude/skills/ui-ux-pro-max/SKILL.md)执行设计系统查询、UX 查询和 React 栈查询。技能临时下载到 `/tmp` 供本次使用，未安装到项目或个人技能目录。

查询记录：

```text
board game lobby minimal              --design-system
minimal community lobby light         --design-system
minimalism accessible                 --domain style
live badge count screen reader        --domain ux
async loading cancellation            --stack react
```

第一轮返回重型 3D 游戏展示风格，与项目不符，未采用。收窄后命中 Minimalism & Swiss Style，采用其简洁层级；生成器附带的营销页结构、紫色配色和远程字体不适合现有侧栏，未直接套用。最终配色和布局是结合仓库现有设计做出的项目决策。

**设计方向：暖纸色棋室，黑白棋子作为轻量装饰，琥珀色突出行动。** 保持现有棋盘的亲和感，通过信息顺序与留白提升大厅可用性。

| 设计项 | 规格 | 来源 |
|---|---|---|
| 页面底色 | `#F7F3EA` | 现有 `--bg-color` |
| 内容表面 | 实色白或接近实色的暖白 | 延续现有白色卡片 |
| 正文 | `#2B251F` | 现有 `--text-main` |
| 次级文字 | `#7D7265` | 现有 `--text-muted`；不用更浅文字承载关键状态 |
| 主要操作 | `#B45309`，白字；悬停 `#92400E` | 现有 accent |
| 可加入状态 | `#15803D`＋「等待中」文字 | 现有 green |
| 错误 | `#B91C1C`＋具体原因文字 | 现有 red |
| 间距 | 8 / 12 / 16 / 24px | 大厅局部统一节奏 |
| 圆角 | 容器 18px，列表项 12px，按钮 8px | 复用既有 token |
| 字体 | 现有系统中文字体栈；昵称输入 16px | 无外部字体加载 |
| 标题与正文 | 标题 18–20px；正文 16px；辅助信息 14px | 窄侧栏保持可读 |
| 图标 | 同一风格的 SVG 线性图标，16–20px | 匹配、刷新、编辑、复制 |

图标按钮实际可点击区域至少 44×44 CSS px，操作间距至少 8px。最终实现需量测文字对比度与焦点可见性；本规划不代表视觉验收已通过。

## 3. 页面结构

大厅使用独立 `/lobby` 页面，棋盘页继续位于 `/`。首次访问在线版本进入大厅，带房号或刷新恢复的会话直达棋盘。

桌面内容上限 1160px，外侧留白 32px。页面顶部是五子棋品牌和「返回棋盘」，下方是主标题与一句引导。主体左侧约 300px，展示昵称、在线统计、快速匹配、开桌及邀请状态；右侧展示在线棋友和房间广场，两者使用单选组切换。760px 以下变成单列，页面中不显示棋盘。

按用户复审调整层级：在线棋友 / 房间广场使用等宽分段按钮，桌面字号 18px、手机 16px，点击区高 48px 起；快速匹配与自己开一桌采用同宽同高卡片（最小高 68px），各配图标、标题和用途说明，两项间距 12px。

组房成功后进入棋盘，连接面板保留「服务大厅 / 房间联机 / 手动信令」入口，其中服务大厅会导航到独立页面。返回大厅不销毁当前房间，已有座位时可选择返回房间或退出。

实际截图由端到端测试生成于 `output/playwright/lobby-desktop.png`、`lobby-375.png`、`lobby-320.png`。

## 4. 模块与关键交互

### 身份与在线统计

- 自动生成「棋友4821」一类昵称；正常浏览和匹配无需先点保存。
- 「修改」原位展开带标签的输入与保存 / 取消；Enter 保存，Escape 取消。合法性错误显示在输入下方。
- 大厅昵称沿用 PRD 的 2–12 字符规则，建议按 Unicode 码点计数，避免 TS 与 Rust 对中文、组合输入计数不一致。旧房间路径的既有昵称规则独立兼容。
- 在线人数与等待桌数来自服务端。加载时显示「正在获取大厅状态…」，失败显示「暂时无法获取在线人数」，不以 0 伪装加载状态。
- 计数不会每次刷新都触发读屏播报；关键异步结果使用一个统一状态区，播报完整语句。

### 快速匹配

大厅初始态「快速匹配」使用琥珀色实心，「自己开一桌」使用暖色描边，两者尺寸和标题层级一致；单桌「加入」使用紧凑按钮。

| 阶段 | 面板显示 | 可执行动作 |
|---|---|---|
| 待匹配 | 快速匹配＋副文案 | 匹配、建房、加入 |
| 请求中 | 按钮显示「正在加入匹配…」 | 防止重复入队；可记录取消意图 |
| 队列中 | 「正在为你寻找对手…」＋已等 `00:12`＋真实统计 | 取消匹配、切换标签或模式 |
| 取消处理中 | 「正在取消…」 | 不允许立即再次入队，等待确认或断线处理 |
| 匹配成功 | 「已匹配到 {昵称}，正在建立连接…」 | 自动走既有房间 / WebRTC 流程 |
| 可以落子 | 棋盘、执子信息与现有对局工具 | 正式对局 |
| 超时 / 失败 | 原因＋重试或创建房间 | 用户主动选择下一步 |

匹配区域原位替换大厅操作区与列表，不盖住标签导航或棋盘。计时使用等宽数字；只在有意义的状态改变时播报，不逐秒朗读。

匹配默认 60s 超时；30s 可出现较久等待提示。匹配到人之后，队列计时结束，改为连接状态，不能继续显示「正在找人」。连接失败必须退出失败的入座状态并提供恢复入口，不冒充开局成功。

取消与配对并发时，由服务端决定最终队列与座位状态。客户端保留本次操作的取消意图：若取消后迟到的匹配结果已产生座位，应释放该座位并通知另一端，不把取消者强行送入棋盘。断网时允许本地回大厅，但需提示连接中断、暂停新网络操作，重连后先清理残留意图。

切到其他标签仍保留匹配，标签显示「匹配中」。切到人机模式时使用顶层轻提示保留可取消入口；匹配成功后提示「对手已就位，返回联机对局」，不强制打断用户当前的人机视图；联机连接流程继续。

### 在线棋友与邀请组房（用户新增要求，P0）

在线棋友页展示大厅中可被发现的在线会话；每项包含默认棋子头像、昵称、状态与操作。默认空闲优先、其他用户按稳定顺序展示，可按昵称搜索并开启「只看可邀请」。每页 20 项，加载更多；搜索全量可发现名册，不能只在已加载首页中查找。搜索无结果与无人在线分别展示对应空态。

| 状态 | 用户项操作 | 说明 |
|---|---|---|
| 空闲 | 邀请对局 | 双方都空闲且连接正常时可发起 |
| 匹配中 | 不可邀请 | 不抢占已进入的随机匹配 |
| 邀请处理中 | 不可邀请 | 自己发出的邀请有取消入口 |
| 等待入座 | 不可邀请 | 已在房间，公开房可从房间广场加入 |
| 连接中 / 对局中 | 不可邀请 | 不打断已有房间与对局 |
| 暂时离线 | 不可邀请，随后移除 | 状态失效即时禁用，服务端再校验 |

当前会话显示「你」，没有自邀按钮。列表中的同名或多标签页会话用服务端提供的公开短标识区分；不暴露真实 peerId、座位凭证、IP 或连接标识。统计口径使用「在线会话」，UI 辅助说明「同一浏览器多个窗口分别显示」，避免把会话数宣称为去重真人数。全局在线统计可以大于当前可发现列表人数。

邀请主链路：

```text
A 在在线棋友里点击 B 的「邀请对局」
  → 服务端确认邀请有效，A 显示「等待 B 接受 · 00:30」与「取消邀请」
  → B 收到「A 邀请你下一盘」卡片，提供「接受邀请」「暂不接受」
  → B 接受，服务端重新校验双方可用状态，原子创建房间并为双方入座
  → 双方显示「对方已就位，正在建立连接…」
  → WebRTC 连接就绪，进入现有棋盘
```

- 邀请卡放在大厅面板顶部，切换标签或人机视图时有轻量入口可查看；不弹浏览器原生确认框、不抢输入焦点、不自动替对方接受。
- 邀请待处理 30s 后失效，以服务端到期时间为准。首期采用固定倒计时；不自动接受，到期后可由用户主动重新发起。减少动效时仍保留静态状态与文字。
- 发起方可取消，接收方可拒绝；状态同步到双方，结束后各自回到原列表位置。拒绝显示「对方暂时不方便」，不自动重发。
- 待接受前不创建房间；接受成功后才创建一间私密双人房，并为双方直接占座。该房不进入公开房间广场，避免第三人抢座；发起方为房主，沿用既有默认执色与换边流程。
- 每个会话最多一条待处理的发出或收到邀请；交叉邀请复用同一条邀请并保留原发起方，不能把反向点击当作自动接受。重复点击不产生多条邀请或房间。
- 收到邀请不阻止用户进行其他活动；接收方主动匹配、建房或加入其他房间时，原邀请立即失效并通知发起方。发起方切换其他联机操作前先取消邀请。
- 接受与取消、超时、掉线或其他入座操作并发时，由服务端原子决策；每条邀请最多建一间房，任一会话同一时刻最多属于一间房或一个匹配队列。客户端取消意图下的迟到入座需要释放，不能把已取消的用户强拉入对局。
- 任一方离线或相关会话被替换时，待处理邀请失效；重连不复活旧邀请。已经接受并入座的会话则复用房间 resume。
- 接口支持单独声明邀请能力；仅支持旧版大厅时，在线列表可展示，邀请入口给出升级说明，不发送不支持的请求。
- 客户端防连点；服务端对发起邀请至少间隔 3s，同一双方会话在拒绝或超时后冷却 60s。失效、拒绝、取消均不自动重发。

在线名册只面向进入在线大厅的会话；本地人机、手动信令与离线单文件不会因此自动公开。后续隐身模式启用时，该会话不出现在可发现名册且不能被新邀请；发出邀请前需退出隐身。与旧 PRD 仅匿名显示的定义差异见 §7。

### 房间列表与加入

每项展示房主昵称、4 位房号、座位数、状态与等待时长。等待中的房间优先，等待越久越靠前；已满项低强调。

- 只有「加入」按钮执行加入；不把整行做成隐形点击区。
- 点击后显示「加入中…」，防止重复请求；服务端校验成功才进入房间视图。
- 房号单独提供复制操作，反馈「房号已复制」，不与加入共用点击区域。
- 服务端以可加入性为准：房主离线、房间满员或已关闭时立即禁用按钮并显示具体文字。
- 加入失败保留当前位置，显示 PRD 对应错误文案并刷新列表一次。
- 实时数据更新时保留正在聚焦的操作位置，避免列表重排让用户点错桌；状态更新和禁用立即生效，重排在交互结束后进行。
- 沿用 PRD 的每页 20 条、最多 100 条与加载更多。大厅标题使用「房间列表」，避免同时展示满员项却统称「可加入的房间」。

满员与对局中不能仅凭人数互相替代。两人入座但尚未连接时显示「满员 / 连接中」；只有存在可靠的就绪状态来源，才显示「对局中」。就绪通知只表达连接阶段，不上报棋谱或聊天内容。

### 创建房间与等待入座

- 大厅「创建房间」沿用既有创建流程，默认公开展示；没有规则表单与额外确认步骤。
- 建房成功后进入既有房间视图：显示房号、复制邀请链接、等待状态，以及「已展示在大厅」说明。
- 原「房间联机」路径新增「在大厅展示」开关，建议默认关闭，以保留原有邀请用户的隐私预期。此默认值需同步进 PRD。
- 对手入座时显示「{昵称} 已加入房间」，自动开始连接。
- 返回大厅浏览只是切换视图，保留座位；大厅顶部显示「你的房间 {房号}」与返回 / 退出入口。
- 已在房间或对局中时，不直接开放新匹配、建房、加入。用户主动选择「退出当前房间」后再操作，避免无意换房。

## 5. 空态、故障与反馈

| 场景 | 显示 | 行动 |
|---|---|---|
| 正在加载 | 身份区域保留，列表区域预留高度并显示加载说明 | 避免重复刷新 |
| 没有等待中的桌 | 「大厅里还没有等待中的房间」；副文案「自己开一桌，等对手来」 | 创建房间 |
| 只有满员房间 | 说明「当前房间都已满员」并保留列表 | 快速匹配 / 创建房间 |
| 匹配超时 | 「暂时没找到对手，试试自己开一桌？」 | 创建房间 / 重新匹配 |
| 加入被抢先 | 「房间已满（仅支持 1v1）」 | 刷新列表，保留浏览位置 |
| 大厅网络中断 | 「大厅连接已断开，正在尝试恢复」 | 重试 / 手动信令 |
| 旧服务器不支持 | 「大厅需要更新后的信令服务器」 | 房间联机 / 手动信令 |
| 重连宽限期失效 | 「上一局已结束」并返回可用大厅 | 重新匹配 |
| 房主暂时离线 | 「房主离线」；禁止加入 | 选择其他房间 |
| 请求限流 | 「操作太快了，休息一下」 | 停止自动重试，冷却后可再操作 |
| 无其他可发现用户 | 「暂时没有其他在线棋友」 | 创建公开房间 / 快速匹配 |
| 在线用户搜索为空 | 「没有找到这位棋友」 | 清空搜索 / 查看全部 |
| 邀请被拒绝 | 「对方暂时不方便」 | 选择其他棋友，遵守冷却时间 |
| 邀请超时 | 「邀请已过期」 | 选择其他棋友 / 快速匹配 |
| 对方状态已变化 | 「对方当前忙碌，暂时无法接受邀请」 | 刷新在线状态，不创建房间 |

Toast 用于复制等短反馈；持续故障放在面板里；昵称错误放在字段旁。纯匹配过程不使用锁焦点弹窗。长列表、昵称修改、取消操作完成后，焦点回到合理的原操作位置。

主按钮即时给按压反馈，异步操作显示处理中。颜色 / 透明度过渡约 120–180ms，内容切换约 180–220ms；只使用少量 CSS 动效，减弱动态效果开启时移除循环动画。无需新增动画框架。

## 6. 开发分步与验收

本次只交付规划。进入开发时按仓库 TDD 规范，先失败测试再最小实现；每步 `pnpm build && pnpm test` 通过，web / server 改动追加 E2E。Rust 变更补充对应模块测试与集成测试。

| 步骤 | 交付 | 先行验证重点 |
|---|---|---|
| 1. 构建与协议边界 | 在线 / standalone 构建拆分方案；大厅能力发现与数据契约 | 无大厅的旧服务端兼容；standalone 不含大厅模块 |
| 2. 在线棋友与房间广场 | 大厅组件、昵称、真实统计、可发现用户列表、公开列表与建房 / 加入 | 状态映射、名册搜索、会话区分、公开 / 私有过滤、排序、校验 |
| 3. 定向邀请 | 可注入时钟的邀请状态机、双端通知、接受后建房入座 | 接受 / 拒绝 / 取消 / 过期、交叉邀请、掉线、重复接受、与其他入座并发 |
| 4. 快速匹配 | 可注入传输与计时的匹配状态机；服务端队列 | 幂等、取消与配对竞态、邀请与队列互斥、超时、迟到消息 |
| 5. 恢复与适配 | 重连、多标签页、故障降级、响应式与无障碍 | 座位归属、取消残留清理、焦点、手机顺序、已有棋局保护 |
| 6. 集成验收 | 双端真实开局与回归记录 | 邀请接受到可落子、匹配到可落子、名单入座、双方取消 / 离开、离线邀请回归 |

建议模块边界：`LobbyPanel` 负责渲染，`useLobby` 负责协调，独立状态机分别负责匹配和邀请行为，传输适配器负责网络。大厅协议与校验进入 shared；服务端大厅名册、公开房间索引、邀请记录和匹配队列独立于棋局规则，通过统一入座协调保证互斥。继续复用现有房间会话与连接编排，不向棋盘加入大厅网络逻辑。

Rust 是 README 推荐的信令服务，Node 是开发 / fallback 服务；落地前明确两者的大厅能力范围。即使分步只接入一种，另一种也必须通过能力发现正确降级，不能出现前端展示可用而服务端不识别请求的情况。

首期完成的判定是：两名新访客无需互发房号即可通过定向邀请或匹配完成真实对局；用户可安全拒绝、取消、恢复和重新加入；在线用户与房间广场可用；原有邀请、人机与单文件路径通过回归。PRD 的耗时和成功率指标属于上线后的测量目标，不能用静态原型或单次本机演示代替。

## 7. 与现有 PRD 需要对齐的具体事项

| 位置 | 现有问题 | 本提案建议 |
|---|---|---|
| §6.1 桌面布局 | 360px 侧栏同时要求两列房间，文字与按钮空间不足 | 保持单列 |
| §3.1、§7.1 入口能力 | 旧服务端时显示占位与不渲染入口的描述不一致 | 网页版保留说明性占位；standalone 构建移除入口 |
| §6.3 / §6.5 空态文案 | 「通常 1 分钟」缺少运营数据支持 | 改为「自己开一桌，等对手来」 |
| §6.5 列表标题 | 列表含满员房间却称「可加入的房间」 | 改为「房间列表」 |
| §3.3 故障引导 | 服务端不可达时「用房间号联机」仍依赖同一服务 | 主要引导到手动信令；房间联机保留原错误与重试 |
| §4 / §6 等待时长 | 已列为 P0，又在 P2 重复出现 | 基础相对时间纳入 P0；长期等待装饰提示可延后 |
| §3.2 公开开关 | 原有建房流程的公开默认值未定义 | 原路径默认私有；大厅建房默认公开 |
| §5 匹配取消 | 本地取消与服务端配对竞争需要明确收敛语义 | 取消意图跨重连保留，迟到座位释放，另一端有失败反馈 |
| §1.2 / L-19 standalone | 当前 Vite 把同一个网页产物复制为 standalone，没有独立剔除路径 | 先拆构建；在同一基线、同一环境下检查大厅引入增量，不能仅运行期隐藏 |
| L-17 与 DoD XSS | 昵称非法字符被拒与恶意字符串可作为昵称展示存在口径冲突 | 写入端拒绝非法昵称；注入展示数据时验证纯文本渲染，分别测试 |
| L-03 对局状态 | 服务端目前不读取 P2P 棋局，不能仅从两人入座推断已开局 | 明确最小就绪状态契约，继续禁止上报对局内容 |
| L-02 在线名册与新要求 | 原文只定义人数统计，没有可浏览用户与定向邀请 | 用户已明确要求，已在 PRD §11 补充为 P0 |
| L-22 / Q5 隐身 | 仅匿名显示仍可定向邀请，无法避免隐身用户被打扰 | 建议隐身不进入可发现用户列表；仍计入在线会话总数，公开房间维持原可见性 |

除用户已明确要求并写入 PRD §11 的在线用户与邀请组房外，其余仍为待合并到需求基线的设计建议；功能尚未实现。
