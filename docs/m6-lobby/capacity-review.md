# 大厅容量与断线广播复审

日期：2026-10-20。基线版本：`5cc125c`；修复版本：`2f6655e`。本次修复限于 Rust 大厅发布机制，测试在本地隔离实例完成，该提交尚未部署。本报告保留本次测量事实；后续缺陷状态见[大厅待办](tasks.md)。

## 已修复的两个问题

1. 每个断线事件在大厅锁内立即向所有人发送完整快照。2000 会话、100 个公开房间、100 人同时断线时，独立探针的一次大厅查询耗时 **27317ms**，但 HTTP 健康检查最大仅 **18ms**；健康检查不能证明大厅仍可用。
2. 即使没有变化，也每秒推送全量快照。2000 会话和 100 个公开房间的聚合下行约 **208Mbps**，超过已确认的服务器 **100Mbps** 公网出口。

修改后的处理：断线立即更新内存状态、取消相关邀请并向对手发送离线通知；名册与房间变化只标记待发布，由现有每秒任务合并发布一次。无变化不广播，主动查询仍单独返回当前状态。旧协议 create/join/leave/resume 同样不再立即全员广播。座位宽限期结束时使房间缓存失效，避免剩余玩家永远看到旧人数。

邀请、匹配成功、座位凭证和对手离线通知继续定向即时发送。协议字段与浏览器每 5 秒主动查询保持现状。本次没有实现 HTTP 查询端点或增量协议。

## 本地容量对比

同机 Linux amd64 release 容器，限制 **2 CPU、512MiB**，Redis 关闭。连接/IP 配额仅在压测实例放宽至 5000；生产实例没有进行压力测试。负载包含所有会话每 5 秒查询一次，加上约 30 次/秒的查询后 ping 采样。带宽统计为所有客户端收到的 WebSocket 消息正文，不含 TCP/TLS/以太网开销。

| 场景 | 修复前下行 Mbps | 修复后下行 Mbps | 修复后查询+ping P95 |
| --- | ---: | ---: | ---: |
| 2000 会话、无公开房间 | 34.85 | 8.13 | 11.59ms |
| 2000 会话、100 个公开房间 | 207.72 | 48.40 | 13.79ms |
| 2000 会话、1000 个公开房间 | 207.95 | 48.55 | 20.18ms |
| 1000 个双人房、2000 个信令座位 | 216.59 | 50.30 | 38.04ms |

基线窗口 8 秒、修复后窗口 15 秒；窗口包含操作后的待发布快照，不是完全静止的带宽下限。房间列表最多返回 100 项，因此 1000 个房间的消息大小与 100 个房间接近。双人房场景模拟信令座位，不等于同时运行 1000 场真实 WebRTC 对局。

100 人同时断线后，第一轮旁观者查询 **9.8ms** 返回，100 个新会话重新进入用时共 **620ms**。这一步验证离线波与重新准入，不把它当作 100 个旧座位恢复。独立进程覆盖这轮压测时，查询最大 **97.38ms**、P95 **11.71ms**；修复前相同探测方式最大 **27317.46ms**。新探针不接收名册广播，避免负载生成器解析大消息造成误判。

1000 个双人房场景的 100 人断线波中，旁观者查询 **27.2ms** 返回，重新准入共 **3032.8ms**；结束后所有测试连接清理耗时 **1015.7ms**。该轮未同时运行额外探针，因此清理统计不包含探针等待。

第 2001 个大厅会话、第 1001 个大厅房间均被拒绝，达到目前写死的容量边界。单 IP 配额与断开后配额释放均测试通过（Rust 100、Node 10）。无房间的 2000 会话另有 3 个 60 秒测量窗口，未发现请求失败；这不是长时间生产稳定性承诺。

100Mbps 出口下，本次低变更频率场景的 2000 会话已在带宽预算内。但持续有人进出、切换状态时仍可能每秒广播一次完整快照，重新接近原来约 208Mbps。不能仅据本次结果宣称生产稳定承载 2000 人，更不能把配置的 100000 个连接当作实测容量。下一步应将名册/房间分页改为 HTTP 按需查询，加短小的增量通知与浏览器可见性订阅，进一步控制活跃大厅的流量。

## 复现入口

先启动独立测试实例；容量测试会大量建房、断线，仅对测试实例运行。所有命令从仓库根目录执行。

```sh
# Rust 功能实例：显式设为 100/IP，供下方配额脚本验证
cargo build --manifest-path apps/signaling-rust/Cargo.toml
GOMOKU_PORT=3115 GOMOKU_REDIS_ENABLED=false GOMOKU_PUBLIC_DIR=packages/web/dist \
  GOMOKU_MAX_CONNECTIONS_PER_IP=100 \
  apps/signaling-rust/target/debug/gomoku-signaling

BASE=http://127.0.0.1:3115 LONG_TESTS=1 node test/lobby-protocol.e2e.js
BASE=http://127.0.0.1:3115 IP_LIMIT=100 node test/lobby-limits.e2e.js
BASE=http://127.0.0.1:3115 node test/lobby-edge.e2e.js
BASE=http://127.0.0.1:3115 REQUIRE_P2P=1 pnpm test:e2e

# 另一个容量实例设置 GOMOKU_MAX_CONNECTIONS=5000、
# GOMOKU_MAX_CONNECTIONS_PER_IP=5000，端口 3114，并禁用 Redis
BASE=http://127.0.0.1:3114 SIZES=2000 PUBLIC_ROOMS=100 HOLD_MS=15000 \
  OUT=output/lobby-fixed-stress.json node test/lobby-stress.js
BASE=http://127.0.0.1:3114 SIZES=2000 PUBLIC_ROOMS=1000 HOLD_MS=15000 \
  OUT=output/lobby-fixed-full-rooms.json node test/lobby-stress.js

# 可在独立终端同时运行探针
BASE=http://127.0.0.1:3114 DURATION_MS=75000 \
  OUT=output/lobby-fixed-probe.json node test/lobby-probe.js
```

`lobby-edge.e2e.js` 对上述两个已知前端问题会返回非零状态，特意保留为复现脚本，没有接入默认全绿回归入口。协议扩展脚本在 Node 上也会报告上述两个问题。原始结果写入 `output/`，压力测试与探针同时运行时，清理统计会等待探针的连接关闭，不能据此推断业务连接清理耗时。
