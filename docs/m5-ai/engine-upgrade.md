# AI 引擎升级与能力边界

## 浏览器计算

人机模式通过 `aiSearch.ts → workerClient.ts → search.worker.ts` 启动并复用一个 Web Worker。搜索和策略复验在 Worker 中执行；React、棋盘绘制和交互留在主线程。请求 ID 隔离不同棋局，切模式、重开和取消后不会接收旧结果。

Worker 以 Blob 内联到构建产物，HTTP 页面和直接打开的 `dist/gomoku-standalone.html` 都可离线下棋。Worker 不可用、初始化失败或消息异常时，自动使用可取消的主线程分片搜索。

一个 Worker 使用一个计算线程，主要改善交互响应；当前没有实现多核搜索池，也没有把 JavaScript 换成 WASM。分片通过生成器保留递归栈与棋盘，暂停后继续同一个候选，不再因分片跳过未完成的候选。连续冲四搜索也遵守时间分片；总预算不足一层时返回合法兜底手，完成深度保持为 0。

## 求胜与证明

普通搜索使用迭代加深、Alpha-Beta、置换表和候选裁剪。高估分、开局策略和有限深度都不能证明必胜。`AiSearchStats.proofStatus` 只有两种状态：

- `win`：`winningProof` 已通过独立规则检查器，可以覆盖当前局面所有合法防守应手。
- `unknown`：没有完整证明；不等于必败或和棋。

困难档在连续冲四之外，增加包含活三的有限预算 AND/OR 搜索。攻击方找到一条胜路即可；防守方必须覆盖全部空点，不能只验证邻近候选。证书支持直接成五、两个立即成五点、强制堵四链、完整防守分支。检查器不依赖棋型估分，按 15×15、交替落子、无禁手、五连或长连获胜的规则复验，也拒绝非法棋谱、缺失分支和循环证书。

## 最强档算法升级（威胁依赖分析 + 证明数搜索 PNS）

为进一步增强最强档在复杂中局的攻杀与防守强度，引擎借鉴证明数搜索（PNS）与威胁依赖分析（db_search）算法思想进行了深度升级：

1. **威胁依赖分析（`dependency.ts`）**：
   - 将棋盘进攻点抽象为 `Threat` 结构（包含成形点 `gain`、防守必堵点 `cost`、后续成形空点 `rest` 与既有棋子 `stones`）。
   - 建立了成五、活四、冲四、活三之间的依赖判定（`threatDependsOn`）与冲突检测，用于排列进攻候选与优先检查反击。
   - 启发式候选排序：成五（50000）> 双四/四三（40000）> 冲四（30000/35000）> 活三（20000/25000），配合方向跳过与预筛选，大幅提升评估效率。

2. **证明数搜索（`pnSearch.ts`）**：
   - 攻击方为 OR 节点（$pn = \min(pn_i), dn = \sum dn_i$），防守方为 AND 节点（$pn = \sum pn_i, dn = \min(dn_i)$），按证明数选择最易证明的路径展开。
   - 防守节点覆盖全盘合法防守应手；优先探索冲四必堵点（`cost`/`rest` 赋予高优先级权重），使非必胜攻击分支在 1~2 步内迅速被反驳证伪，极大地压缩了 AND 分支的探索规模。
   - 证明边界严格守住：搜索结果转换为现有 `WinningProof`（`five` / `force` / `branch`），经独立检查器 `verifyWinningProof` 复验通过后方可采用。节点耗尽、深度不足、超时或取消均安全返回 `unknown`，绝不解释为必败。

3. **最强档执行流程与预算分配**：
   - 每步总思考时间预算调整为约 **3000ms**。
   - **流水线**：已验证策略/开局知识 → 快速连续冲四（最多 300ms，mode: `'fours'`）→ PNS 求胜（最多 1200ms，mode: `'threats'`，上限 8 次进攻、20000 节点）→ 根候选反杀防守检查（最多 600ms，每个候选最多 6 次进攻、512 节点，上限 14 手）→ Alpha-Beta (Negamax) 主搜索。
   - 未消耗完的时间预算顺延给后续阶段，证书复验计入预算。
   - 反杀防守检查增加了活三威胁，采用分阶段策略（快速 VCF 先行 + PNS 活三检查），只排除有已验证反杀证书的候选；所有候选均被反杀时保留正常搜索，让 AI 选择最顽强的抵抗路线。

## 黑先能否「立于不败之地」的能力边界

关于最强档 AI 执黑先行能否做到“绝对不败”，需明确区分数学博弈理论与当前工程实现的边界：

1. **数学博弈论事实**：
   - **15×15 无禁手五子棋（Freestyle Gomoku）早已被证明是先手（黑方）必胜**（Victor Allis 于 1993 年使用证明数搜索和威胁数据库严格证明）。
   - 在纯数学层面，黑棋只要每步都走理论最优解，白棋无论如何防守最终都会被强行连续冲死。

2. **当前实战表现（对人类“几乎不可战胜”）**：
   - **天元开局**：AI 首手固定落子天元 `(7,7)`，迅速建立中心控制。
   - **强大的中局斩杀力**：一旦棋盘进入中盘（通常在 7~11 手），局面只要出现活三或冲四攻击机会，PNS 证明数搜索能在 8 次进攻深度（十余步应手交锋）内精准抓到必胜路径并走出必杀。
   - **反杀自检防守**：在落子前会扫描白棋的活三与连杀反扑，避免走出“看似占优实则被反杀”的漏洞走法。
   - 因此对普通玩家及高水平业余爱好者，最强档执黑具有极高统治力，几乎无法被击败。

3. **工程边界（为何不声称 100% 绝对不败）**：
   - **未内置全盘离线必胜库**：完整证明 15×15 黑棋全分支必胜的数据量极大（压缩后通常达数十 MB 至数 GB，如专业五子棋引擎 Yixin 的开局库）。本项目定位为零依赖纯轻量化客户端单文件运行，不携带超大规模预计算局面库。
   - **思考预算有界（约 3 秒）**：在开局第 3~9 手空旷阶段，尚未形成紧凑攻击链，PNS 无法直接给出证明，需依靠 Alpha-Beta 评估。在 3 秒限制下，主搜索深度一般在 8~12 层，尚未具备单步穿透到终局的能力。
   - 若遇到预先背诵了极端冷门必败防守分支的顶尖特化研究者或特化软件，纯现场 3 秒计算的黑棋理论上仍存在微小概率在深层分支走出次优手导致优势流失。未来若需达成 100% 全局不败，需引入完整的离线预计算必胜数据库作为知识基底。

## 离线求解与复验

输入按黑白交替给出坐标，范围为 0–14。`maxAttacks` 计攻击方落子的次数，`maxNodes` 限制搜索节点。时间源由 CLI 注入，core 没有 IO 或全局时钟。

```sh
pnpm ai:prove docs/m5-ai/examples/double-three.input.json /tmp/double-three.proof.json
pnpm ai:verify /tmp/double-three.proof.json
```

参数支持 `algorithm: 'dfs' | 'pn'`，默认保留现有 DFS，最强档显式使用 PNS。输出文件必须尚不存在。成功时写入 `gomoku-proof-v1` 证书，退出码为 0；预算不足或未找到证明时写入 `gomoku-search-v1`，退出码为 2；非法输入或复验失败时退出码为 1。示例双活三用 217 个搜索节点得到证明，覆盖 216 个防守应手；对应证书也保存在本目录 `examples/double-three.proof.json`。

搜索模式：`fours` 只找连续冲四，`threats` 包含活三，`complete` 枚举全部攻击点。三种模式都完整验证防守。`complete` 仍受深度、时间、节点预算限制，不代表已经解出空盘。

## 验证记录

- 分片与不分片落点一致，连续冲四与 PNS 可暂停、恢复、取消，极小分片仍能推进。
- 四方向、长连、双活三全应手证明、对手反杀、证书篡改、非法棋谱、预算耗尽均有单测覆盖。
- 固定至少一个进攻局面和一个防守局面，证明新算法（PNS+活三）在**相同节点预算**下显著优于旧算法（DFS）。
- 战术基准集 20/20 题全数通过（一步成五 ×4、堵成五 ×4、活三防守 ×4、双三双四 ×4、三步连杀 ×4）。
- 浏览器验证 Worker 复用、取消、重开、HTTP 离线、`file://` 离线及无 Worker 回退；原有双人联机端到端回归通过。
- `pnpm build`、全量 655 项单测通过（耗时约 3s）；全部联机及 AI 端到端测试（`node test/ai-e2e.js` + `node test/e2e.js`）全绿。
- Monorepo 全部包（`core`、`shared`、`web`、`server`）通过 `tsc --noEmit` 严格类型检查，0 错误。
- 本机 Chrome 实测 Worker 模式下主线程定时器最大间隔 13–17ms，未观测到超过 100ms 的主线程任务。

运行：`pnpm build && pnpm test`，浏览器回归：先 `pnpm start`，再 `pnpm test:e2e`。浏览器测试支持 Playwright Chromium 或系统 Chrome。
