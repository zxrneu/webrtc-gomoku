# Rust/WASM 接入实际对弈搜索

2026-10-22，将现有 `gomoku-kernel` 的方向评分与假设落点评分接入完整生产搜索。TypeScript 仍负责迭代加深、Alpha-Beta、置换表、VCF/PNS、反杀检查、分片与独立证书复验。离线 Rust 证明求解器没有迁入浏览器，既有固定深度 WASM 原型也没有替代完整对弈算法。

## 使用与回退

人机对弈顶部“引擎”选择器可选择 Rust/WASM 或 TS，默认 Rust/WASM，并在本地记住选择。切换保留棋盘，取消旧分析；当前对手回合重新搜索，AI 提示按新选择重新请求。首次打开页面加 `?aiEngine=ts` 或 `?aiEngine=rust-wasm` 可覆盖本地偏好，进入页面后仍可通过选择器切换。调用接口也可传 `AiOptions.backend`。Worker 的 `stats.backend` 返回实际使用的评分后端。WASM 不可用时回退 TS；Worker 不可用或运行异常时使用原有主线程 TS 搜索。

每个搜索会话独立实例化 WASM 内存，落子与撤子同步双方棋盘，支持交错推进、取消、悔棋、重开和提示。证书检查仍以 TS 规则单独执行；已有证书直接执行时不调用评分内核，报告 TS 后端。

## 同生产算法实测

环境为 Node v26.3.0、darwin/arm64，包含会话构造与 WASM 初始化耗时。数据为六个显式局面，固定节点测试交替执行 TS/WASM 三轮，共 18 对。固定测试使用 `maxDepth=12`、常规节点预算 8000、VCF 512、PNS 1024，独立算杀预算与生产引擎保持相同计数规则。

- 18 对的落点、分数、节点数、完成深度、证明状态和终止原因全部一致。
- 固定工作量累计耗时比 TS/WASM 为 1.0823，即本次 WASM 总耗时约少 7.6%。
- 四个中局使用相同 hard 配置、每次 1000ms 搜索预算，WASM 总节点数约多 4.6%，四个落点一致。其中一个局面两端都提前完成深度 16。
- 以上为本机小样本。没有测定棋力提升，也不能把结果解释为整个搜索已迁至 Rust；浏览器不同设备需要各自测量。

原始逐局结果见 [JSON 报告](wasm-production-report.json)。重跑：

```sh
pnpm ai:bench:wasm --budget=1000 --nodes=8000 --output=output/playwright/wasm-production-benchmark.json
```

## 验证

单测覆盖实际 WASM 调用、相同节点预算的一致性、两个会话交错执行、落子/撤子恢复、独立证书复验、零预算、取消、WASM 不可用回退、Worker 工厂注入与消息参数校验，以及引擎选择的持久化与搜索取消。浏览器回归包含 HTTP 页面、TS 对照、单文件离线和 Worker 不可用路径；引擎选择覆盖手机布局、思考中切换、棋盘保留、提示跟随、忽略过期响应和刷新记忆。

本次 `pnpm build && pnpm test` 通过：83 个原生 Rust 测试、89 个文件中的 1317 个 Vitest 测试全部通过；网页严格类型检查通过。完整 `pnpm test:e2e` 通过，包含上述四种 AI 运行方式，以及页面导航、棋盘、P2P、聊天、富媒体、大厅和 HTTPS 回归。浏览器实际 Worker 消息确认默认使用 `rust-wasm`，TS 对照使用 `ts`。
